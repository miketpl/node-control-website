Back up running configs from mixed vendors in one run

Last updated 11 November 2026

A useful backup is the running config, captured completely, named so you can find it later, and taken with an account that only needs to read. On a mixed estate that means a different command on each vendor, and a pager that will happily write “--More--” into the file if you leave it on.

This page is the manual method first. Then it shows how Config Backup in Node Control runs the vendor command for you, across the devices you tick, in one go.

The file name example below uses a documentation address (192.0.2.10). Use your own values in the lab.

The command each vendor needs

These are the running-config commands I would run by hand. The first five, and the VSP line, are also the commands the Node Control docs name for Config Backup. The others need a check on my lab before this page goes live.

Vendor Running config Saved / startup, if there is one
Cisco IOS, IOS-XE, NX-OS, and Arista EOS show running-config show startup-config
Juniper Junos show configuration | no-more There is no startup variant
Palo Alto PAN-OS show config running show config saved
Dell OS10 show running-configuration [VERIFY] confirm the startup form on the lab
Extreme VSP show running-config [VERIFY] confirm the startup form on the lab
Aruba AOS-CX [VERIFY] Node Control docs say Aruba has its own variants, but they do not name the command. A typical candidate is show running-config. Confirm running and startup on the lab.
Aruba OS-Switch / HP ProCurve [VERIFY] not named in the docs. Confirm running and startup on the lab.
Dell OS6 [VERIFY] not named in the docs. Confirm running and startup on the lab.
Extreme EXOS [VERIFY] not named in the docs. A typical candidate is show configuration. Confirm running and startup on the lab.

Pager gotchas

Most CLIs pause long output with a pager. If you capture a session without turning that off, the file contains “--More--” prompts, or it stops early, and the backup is not a complete config.

Junos is the easy one: | no-more is already in the command above. On Cisco IOS, IOS-XE, NX-OS and Arista, I would run terminal length 0 first. On PAN-OS, the usual form is set cli pager off. Aruba OS-Switch often uses no page.

[VERIFY] Pager-off commands

Every pager-off form on this page needs a lab check, including the PAN-OS and Aruba OS-Switch lines, and the AOS-CX, Dell, EXOS and VSP equivalents, which I have not named because they are not in the Node Control docs.

When you finish, set the pager back if other people share the session. And do not treat a truncated capture as a backup. If the file is shorter than you expect, or it contains a pager prompt, take it again.

How to name the files

Give every file a name you can sort and search later: the device, the address, whether it is running or startup, and a timestamp. Node Control writes one file per device in this form:

<hostname>_<ip with underscores>_<running|startup>_<YYYYmmdd_HHMMSS>.txt

For a documentation example:

core-sw1_192_0_2_10_running_20261111_090000.txt

One timestamp covers the whole run, so a batch taken together stays grouped. Keep the files in one folder per run, or in a folder you already back up. The content is the device config, so treat the folder as sensitive.

Why read-only matters

A backup should not change the device. Use an account that can read the running config and nothing more, where the vendor allows it. That way a typo, a mixed-up session, or a paste into the wrong window cannot write to the box.

There is one documented exception on Aruba AOS-CX: an operators-level login cannot read the config. You need an admin or manager user, or the backup is empty. Do not save an empty file and think you have a backup.

Pulling the running config is also not the same as saving it on the device. Writing running into startup is a separate change, and it should be a deliberate one.

How Node Control does it

In Node Control this is Config Backup. You tick the devices, choose Config Backup, pick credentials, and choose running or startup. The default output folder is <Output Directory from Settings>/connection_manager/backups. The task is read-only. It is allowed in Safe Mode. It runs the vendor command from the catalogue, through the safe-send allowlist, and writes one file per device in the naming scheme above.

A row shows Backed up or FAIL, and the summary is in the form Complete - X saved, Y failed. Output: <dir>. Dry run logs the commands and the file it would write, without writing it. Stop cancels the run. On AOS-CX, if the login cannot read the config, the task tells you an admin or manager user is needed and does not save an empty file.

On Extreme EXOS, Config Backup saves the file only if the configuration looks complete. A short read, a missing section compared with an earlier backup of the same switch, or an account without permission, is not saved, and the row says why. The first backup of a switch is read twice and saved only if both reads match.

Save Config is a different task. It writes the running configuration into the saved config on the devices you tick. It also runs on Free and Professional, but Safe Mode hides it, because it changes the device.

On Professional you can also run a Config Compliance Audit against your own baseline, without pushing anything, and Config Push with a snapshot and revert. Full push-and-revert support is documented for Cisco IOS, IOS-XE and NX-OS. On Junos, revert restores the snapshot taken before the push; if that snapshot could not be taken, the revert is marked as manual. Other vendors get a template only, with no reliable revert.

[VERIFY] Scheduled backups are not claimed here

The SEO outline said Professional includes scheduled backups. That is not in the current website docs. The website brief says scheduled backups come with Node Control Server, not the current desktop editions. This draft omits them. Confirm before anyone adds that sentence back.
